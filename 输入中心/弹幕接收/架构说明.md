# 弹幕注意力打分系统 架构说明

## 一、目标

给每条弹幕打一个 0-1 的"回复欲望分"，决定：秒回 / 攒几条一起回 / 丢弃。

---

## 二、放弃过的方案

| 方案 | 为什么放弃 |
|------|-----------|
| **B站开放平台** | ✅ **已转正（2026-08-11）**：app_id+access_key 申请通过，「弹幕读取器」项目，默认采集方式 |
| **Cookie 登录 (Web端)** | 会过期、-352 限流、不稳定；uid=0 模式下名字打码 |
| **blivedm 库** | 依赖 SESSDATA，跟 Cookie 方案同样的问题 |
| **BLC 弹幕姬 relay** | BLC v1.10.3 的 WS relay 有 from_dict bug，采集器连不上 |
| **浏览器 hijack 劫持** | DOM 格式不稳定，且 WSL 连不到 Windows localhost |
| **公网代理 blive.deno.dev** | 404 已下线 |
| **BERT 回归训练 (第1次)** | 688条数据中 83% 分数≈0，模型偷懒输出均值，MAE 0.029 但 r=0.38，实际预测全塌缩到 0.015 附近 |
| **Twitter 回复概率模型** | Twitter 是广播媒介，弹幕是群聊，行为模型不兼容 |
| **SSE 推送消费 (19000 /events)** | 长连接状态管理坑多：socket 超时后 http.client 无法再读（`cannot read from timed out object`）、连接维护复杂、断线即丢消息且无重放 → 弹幕消费端放弃 SSE，只用轮询 |
| **游标增量 (seq + 缓冲 + last_seq)** | 需要自增序号/环形缓冲/客户端游标三件套，复杂度远超单消费者场景，且重启重放/桥重启漏读处理繁琐 → 被「读后清空」取代 |

## 三、最终方案：启发式打分 + BERT预留

```
弹幕文本 → scorer.py (纯规则, 基于实证论文) → 0-1 分数
                                    ↓
                          (未来) 训练 BERT 回归替换规则
```

### 数据链路（读后清空 wait 哨兵，2026-08-08 定稿）

```
B站开放平台 WS / B站 WS 弹幕 / curl POST /text
  ↓ blc_collector（open_live 默认 / wbi fallback）→ _store_line：逐行追加到 _store['弹幕']
桥 19000（_store['弹幕'] 初始 'wait' = 无新消息）
  ↓ danmaku_server 每 0.5s GET /take（原子：返回内容 + 置 wait）
弹幕接收 18776：非 wait 则逐行解析 → 打分 → 分块
```

**采集模式（2026-08-11 开放平台转正）**：
- `--mode open_live`（**默认**，合法稳定）：`/v2/app/start {code身份码, app_id}` → wss_link + auth_body → WS 发 op7 鉴权帧 → 收 `LIVE_OPEN_PLATFORM_DM`（`uname`/`msg` 字段）→ 20s 应用心跳 + 30s WS 心跳 → 断线自动重连（重新 start）
- `--mode wbi`（fallback）：旧版自写 WS + WBI 签名（getDanmuInfo，不稳定）
- **身份码可配置**：`blc_config.json`（同目录，页面 19000 可改）优先，`OPEN_LIVE_CODE` 常量兜底；改码 3s 内自动重连生效
- **上桥格式不变**：`_store_line(f'[{uname}] {msg}')` → 下游 danmaku_server 零改动
- 凭证：access_key_id/secret（开发者身份）+ app_id（应用「弹幕读取器」1786938510612）+ code（主播身份码，play-live.bilibili.com 右下角）——**未上架应用只能连开发者本人直播间**

- **读后清空**：消费者读完就把桥置回 `wait`，下一轮读到 wait = 没新数据；新消息写进来自然不是 wait。单消费者天然不重复，无需游标。
- **原子读清**：`/take` 在桥端同一把锁内完成「返回 + 置 wait」，避免「先读后清」两步之间的竞态（新消息被误清）。
- 桥端 `/source_last` 保留给 pipeline 等其他轮询消费者；`/text` 的弹幕行只走 `_store_line`，非弹幕 source 才覆盖存储。
- SSE（/events）已删除：弹幕消费端不需要长连接。

## 四、三阈值总分架构（已锁定 v2）

```
弹幕进入 → scorer打分(0-1) →
  ├─ 分 ≥ 秒发阈值 → 🔫秒回（已存弹夹 + 本条 一起发射输出桥，清空已存）
  ├─ 丢弃阈值 ≤ 分 < 秒发阈值 → 进已存(弹夹)
  │   └─ 已存总分 ≥ 组合阈值 → 📤自动发射全部已存到输出桥
  └─ 分 < 丢弃阈值 → 🗑丢弃
```

- 阈值在页面可动态编辑（秒发/组合/丢弃），持久化到 dm_config.json。
- **已存(saved)即弹夹**：0.11~0.30 的弹幕自动进已存，已存块顶部显示总分，总分超组合阈值自动发桥并清空。
- 发射目标 = 输出桥（dm_config.json `out_bridge`，页面可配；当前配置 18008）。
- 所有发射动作（秒回/弹夹自动/手动 flush）都会记录到页面最右「已发送」列，即使输出桥不可达（发射失败）也保留记录。

### 发射冷却 + 待发射队列（2026-08-09）

```
触发发射条件（秒回 / 组合自动 / 手动 flush）
  → 全部进「待发射队列」pending_fire（一组一组，不丢信息）
  → _fire_scheduler 调度线程（每 0.3s）：距上次发射 ≥ cooldown（默认 5s，可配）
    → 取队头一组发桥 → 更新 last_fire_ts
```

- **为什么排队**：冷却期内再触发不丢弃——攒成一组合并发射，一组一组往外发，信息不丢、刷屏可控。
- **冷却可配**：页面「冷却 [N]s 保存」→ `_config['cooldown']` 持久化 dm_config.json（与阈值同机制），调度实时生效不用重启。
- **手动「发送已存到桥」也走队列**（尊重冷却），提示"已加入待发射队列 N 条"。
- **前端**：操作按钮下新增「待发射队列」面板——每组一个黄色边框框（组号 + 条数 + 内容），面板右侧显示冷却状态（就绪 / 冷却中 x.x s / 冷却 x.x s 后发射下一组）；SSE state 推送带 `fire_remaining`。
- 三个发射点（`_process_danmaku` 秒回 / `_auto_flush_saved` 组合 / `/api/flush` 手动）统一走 `_enqueue_fire()`；`_fire_to_bridge` 只剩调度线程调用。

### ⚠️ 死锁修复（2026-08-11）

**问题**：08-09 改版让 `_enqueue_fire` 用 `_state_lock`（非重入锁），而 `_process_danmaku`/`_auto_flush_saved` 已持有 `_state_lock` → 同一线程二次取锁 = **死锁** → 读桥/处理线程永久卡死（现象：19000 桥上弹幕堆积、页面不更新、SSE 无推送）。

**修复**：三把锁职责分离，锁序单向 `_state_lock → _fire_lock → _sent_lock`：
- 新增 `_fire_lock`：只保护发射队列字段（`pending_fire`/`fire_seq`/`last_fire_ts`）
- `_enqueue_fire` 用 `_fire_lock`（任何持 `_state_lock` 的地方可安全调用），`_fire_scheduler` 取组也用它
- `_fire_scheduler` 持 `_fire_lock` 时从不取 `_state_lock` → 无环路，物理不可能死锁

### 自动刷新按钮（2026-08-11）

- 后端新增 `GET /api/state`（全量状态 + `fire_remaining` 冷却倒计时，与 SSE state 事件同构）
- 前端「🔄 自动刷新」按钮：开启后 1s 轮询 `/api/state` → `updateState`（SSE 兜底，断流也能刷）
- `updateState` 有 `_feedLen`/`_sentLen` 去重，轮询 + SSE 并存不重复渲染

### 参数设计理由

- **秒回阈值 0.30**: 当前最高分 0.73 (名字+问号+异议组合)，0.30 ≈ 基线0.08 + 一个核心特征(问号/名字)。刚好把"打招呼"、"简单提问"、"被点名"全兜进去。
- **弹夹上限 0.30**: 单条 0.12 的普通互动攒 3 条就够发，模拟真人"扫一眼弹幕挑几条回"。
- **丢弃阈值 0.11**: 略高于基线 0.08，把纯666/走神儿/单字全部过滤，但 0.12 的弱互动(如 `主播好可爱`)允许进入。

### 688 条真实数据测试结果

```
总数688  秒回: 72 (10.5%)  进弹夹: 12 (1.7%)  丢弃: 604 (87.8%)
秒回84次  弹夹发射3次
```

## 五、为什么还没用动态阈值（热度自适应）

论文已明确：群聊回复概率 R ∝ 1/(1+N/k)，N=活跃人数，k=人格参数。

但当前缺少硬币本人的开播实测数据。计划流程：
1. 固定阈值跑通生产（当前）
2. 开播时记录每条弹幕的{分数, 到底回了没}
3. 拟合真实的 R(N) 曲线和 k 值
4. 替换为动态阈值
